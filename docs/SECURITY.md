# Security

Deploying an accounting product means the data must be trustworthy and private.
Each item below links to its evidence: a config, a test, or a command output in
[`evidence/G5-security.md`](evidence/G5-security.md). Items that need the real
cloud deploy or a domain are marked as such rather than ticked.

## 1. Secrets

- [x] No secret in git. `.env` is gitignored; only `.env.example` (no secrets) is
      committed. History scanned: the only hits are test fixtures.
- [x] Secrets come from the platform store: Render env vars (`generateValue`,
      `fromDatabase`, `sync: false`) in `deployment/render.yaml`; never in images.
- [x] `INTERNAL_API_TOKEN` is generated by the platform (`generateValue: true`)
      and shared to the reporting service with `fromService`.
- [x] **Production refuses to start without its secrets:** missing/short
      `INTERNAL_API_TOKEN`, missing `DATABASE_URL`, or `CORS_ORIGINS` unset/`*`
      all throw at boot, so a misconfigured deploy fails its health check instead
      of running open (`packages/shared/src/http.ts`, tests in `http.test.ts`).
- [x] The app connects as a dedicated least-privilege role, not the owner (§7).
- [x] Rotation rehearsed for both the internal token and the app DB password:
      old values rejected, new values accepted, APIs healthy throughout.

## 2. Service-to-service boundary

- [x] `/api/internal/*` requires `Authorization: Bearer $INTERNAL_API_TOKEN`,
      compared in constant time (`tokensMatch`, SHA-256 then `timingSafeEqual`).
- [x] It returns per-account totals only. The old `/api/internal/postings`, which
      exposed every journal line, was removed.
- [ ] Not reachable from the public internet: Cloudflare rule blocks
      `/api/internal/*` at the edge (`deployment/cloudflare/README.md`). Requires
      the domain (G6). Until then the token is the only control.
- [x] Evidence: no token → `401`, wrong token → `401`, right token → `200`
      (`ledger-api.test.ts` "guards /api/internal" and the rehearsal).

## 3. CORS

- [x] `CORS_ORIGINS` is the exact dashboard origin; startup fails in production
      if it is unset or `*`.
- [x] `*` only in local development (the default when `NODE_ENV` is not production).
- [x] A foreign origin is not echoed back: verified by test and with `curl -H
"Origin: https://evil.example"` against the rehearsal stack.

## 4. Transport and headers

- [x] APIs send `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`,
      `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
      `Referrer-Policy: no-referrer`, and `Content-Security-Policy: default-src 'none';
frame-ancestors 'none'` (JSON responses are never documents).
- [x] Dashboard sends HSTS, nosniff, `X-Frame-Options: DENY`, `Permissions-Policy`,
      and a CSP whose `connect-src` lists only the two API origins (set at run time,
      `deployment/nginx.conf.template`; Render static headers in `render.yaml`).
- [ ] HTTPS-only redirect and TLS 1.2+: provided by Render's edge and, with G6,
      Cloudflare "Always Use HTTPS" + Full (strict). Verify on the real deploy.

## 5. Input and output

- [x] Every request body and query string validated with Zod at the boundary
      (`parseBody` / `parseQuery`); dates must be real calendar days.
- [x] Money is integer minor units; amounts capped at `Number.MAX_SAFE_INTEGER`;
      floats rejected.
- [x] Request bodies over 64 KB are rejected with `413` before parsing.
- [x] Errors never leak stack traces, SQL, hosts or secrets: `onError` returns a
      generic 500 (test "never leaks internals in a 500").
- [x] Pagination bounded (`pageSize` ≤ 200).

## 6. Rate limiting and abuse

- [x] Per-IP fixed-window limit in each API on public `/api/*`: ledger 300
      req/min, reporting 120 req/min (`RATE_LIMIT_PER_MINUTE`); `429` with
      `Retry-After` and `RateLimit-*` headers. `/health` and token-guarded
      internal calls are exempt.
- [x] The client key is the right-most `X-Forwarded-For` entry (the one the
      platform proxy appends), so a client cannot reset its count by spoofing.
- [x] Evidence: a 700-request burst through the load balancer was throttled
      (`429`s returned); unit tests cover the limit, Retry-After and spoofing.
- Known limit: counts are per instance (2 instances → up to 600/min per IP).
  The authoritative limit is the Cloudflare rule on `/api/*` (G6).

## 7. Database

- [x] Runtime role `ledgerlab_app` (`0003_app_role.sql`): `SELECT, INSERT` on the
      three tables, `UPDATE` only on `accounts.is_active` and
      `journal_entries.status`; `SELECT` only on the balance rollups, which only
      owner-run triggers write (`0004`). No `DELETE`, no `TRUNCATE` (which would
      bypass the append-only triggers), no DDL. Migrations run as the owner via
      `MIGRATION_DATABASE_URL`.
- [x] Verified on Postgres 16: the role runs the full workload and is denied
      `TRUNCATE`, `DELETE`, column updates it does not need, `CREATE TABLE`, and
      dropping the integrity triggers (`repository-contract.test.ts`).
- [x] The ledger's invariants are enforced by the database itself (balanced
      entries, append-only history, `POSTED → VOID` only); see `DATABASE.md`.
- [ ] Private network only, encryption at rest/in transit, backups and a tested
      restore: Render managed Postgres provides the first three; the restore
      drill is in the infrastructure plan (G9).

Creating the role (once per environment, by an operator, password from the
secret store; then deploy so `0003_app_role.sql` applies the grants):

```sql
CREATE ROLE ledgerlab_app LOGIN PASSWORD '<from the secret store>';
```

Put `postgres://ledgerlab_app:<password>@<host>/<db>?sslmode=require` in the
ledger service's `DATABASE_URL`. Rotate with `ALTER ROLE ledgerlab_app PASSWORD
'<new>'`, update the secret, redeploy.

## 8. Dependencies

- [x] `pnpm audit --prod`: clean. `drizzle-orm` upgraded 0.38 → 0.45.3 for

## 9. Cloudflare layer (bonus, G6)

See [`deployment/cloudflare/README.md`](../deployment/cloudflare/README.md):
proxied DNS, TLS Full (strict), WAF managed rules, the `/api/*` rate-limit rule,
the `/api/internal` block, cache rules that bypass the API, and origin locking.

## 10. Known gaps (stated honestly)

Real auth and multi-tenancy are **out of scope** for this test. This is the
biggest gap: today anyone who can reach the API can post entries. How to close it:

- **Authentication:** an OIDC provider (Auth0/Clerk/Cognito), short-lived access
  tokens verified by both APIs, refresh-token rotation, MFA for owners.
- **Authorisation:** a `business_id` on every table, enforced by Postgres
  row-level security keyed on a per-request setting, so one missed `WHERE` cannot
  leak another business's books.
- **Audit:** an append-only `audit_log` (who, what, when, from where) written in
  the same transaction as each post/void/deactivate. The ledger is already
  append-only; this adds the actor.
- **Isolation:** schema- or database-per-tenant for regulated customers (the bank).
- **Abuse:** with users, rate limit per user/business, not only per IP.
